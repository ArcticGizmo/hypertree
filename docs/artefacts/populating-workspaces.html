Hypertree · design brief

Filling the rooms is a
different job than building them.

Arranging desktops is spatial and reflexive — you already do it mid-flow. Populating them is context-heavy and deliberate: what runs here, in which folder, on which screen. The current builder treats both as one big grid, and that's why setup feels like work. This is a brainstorm of ways to make populating its own, lighter act — keyed on the one thing it really turns on: context.

01 The split

Two modes hiding in one screen

A branch of empty desktops is just labelled space — free to make, easy to rearrange, no thinking required. The moment you decide what lives there, the cost changes. Naming the modes separately is the first move.

Structure

Arranging rooms

  • Context-free — a name and a place
  • Cheap, reversible, done constantly
  • Spatial: dive, surface, drag on the board
  • Already fast today
Populating

Furnishing a room

  • Context-bound — a folder, then commands
  • Deliberate, occasional, easy to get wrong
  • Command-oriented: what to run, where, which monitor
  • Needs focus — one room's worth at a time

On the name: Populate and Set up both read well; "Furnish" and "Equip" are more playful. Whatever it's called, it deserves its own verb and its own key — a signal that you're switching from arranging to outfitting.

02 The lever

Almost everything hangs off the working directory

Look at a real dev desktop and the commands all point at the same place — a repo, usually a worktree. Say that place once and the commands collapse to almost nothing.

Without a context

code C:\repos\app

wt -d "C:\repos\app"

pwsh -NoExit -Command "cd C:\repos\app; npm run dev"

With context = C:\repos\app

code .

wt

npm run dev

So context isn't a per-command afterthought — it's the primary input, set at the desktop (or the whole workspace) and inherited down. And once context is a named slot, a layout stops being tied to one repo: parameterise it as a token like {repo} and the same populate recipe outfits any project. That's the straight line back to the founding idea — htree populate <worktree> spinning up a whole environment for a branch you just created.

03 Three shapes

Ways the journey could go

Not exclusive — each picks a different stance on where you author, when it runs, and how much is on screen at once.

A

Fill the room you're standing in

in-place · just-in-time · one desktop · Ctrl+Alt+E
  1. Dive into a branch and land on an empty desktop.
  2. Press the populate chord. A panel opens for this desktop only — its monitors as slots, a context field on top.
  3. Set the context: a folder, or “inherit from the branch”.
  4. Type a command or two per monitor — code ., wt, npm run dev — each inheriting the context as its working directory.
  5. Run now: they launch and land on their monitors — and the desktop quietly remembers them.
StrongNo context-switch; you outfit the room you're in. Tiny surface. Rides existing dive/surface muscle memory.
CostNo bird's-eye view of the whole branch; you move desktop to desktop (which is the point, but some will miss the map).
B

One layout, any repo

context as a parameter · reusable · the worktree dream
  1. A populate recipe declares a token up front: {repo}.
  2. Commands are written against it — code {repo}, wt -d {repo}.
  3. Applying asks once: “Context?” You pick a folder — or it's the git worktree you're on.
  4. The same recipe outfits this project. Tomorrow, a different folder, same layout.
StrongAuthor your dev layout once, reuse forever. This is the payoff Hypertree's name promised.
CostA token is a concept to learn; some commands still want per-command args on top.
C

A guided setup pass

wizard · desktop-by-desktop · never more than one on screen
  1. Start from an empty branch (rooms only).
  2. “Populate…” walks you through one desktop at a time: Desktop 1 · api — what runs here?
  3. Set its context, add its commands, Next.
  4. At the end: run it now, save it as a recipe, or both.
StrongTurns the overwhelming grid into a calm sequence. Great the first time you build a workspace.
CostLinear; poor for tweaking a single desktop later — which is exactly what shape A is for.
04 The decisions underneath

Four dials, set independently

The shapes above are just presets on these. Worth choosing each on purpose.

Context source
A folder per desktop · one folder for the whole branch · a token supplied on apply · derived from the git worktree you're on
Focus scope
The whole-branch grid (today) · one desktop at a time · down to one monitor slot
Timing
Run it now (populate the live desktop) · author a recipe to apply later · both from the same act
Memory
Ephemeral — just launch and forget · remembered on the desktop · promoted to a named, reusable recipe
05 A recommended weave

Context-first, one desktop at a time, doing and authoring at once

The shapes reinforce each other. Make context the first field (dial 1), scope the surface to one desktop (dial 2), let it run now and be remembered (dials 3–4), and give it a dedicated key. You outfit the room you're in; the reusable recipe falls out as a byproduct — no fragile auto-capture, because you typed the commands.

on an empty desktop → Ctrl+Alt+E → set context → commands per monitor → run & remember

Repeat per desktop as you move through the branch. “Save as recipe” promotes what you built; re-applying it later asks only for a new context. Whole-branch editing (the current builder) stays as the power-user view for reordering everything at once.

06 Still open

Questions worth deciding before building

Monitors inside a single-desktop focus

One desktop still has three screens. Slots left-to-right, or a “default monitor” with per-command overrides? Most commands probably don't care which screen — so maybe monitor is optional, not front-and-centre.

How context is supplied on apply

A typed path, a folder picker, recent folders, or — the good one — the worktree Hypertree already knows you're in. Ordering matters: the worktree case should be one keystroke.

Per-command escape hatch

Inheritance covers the common case; some commands need their own directory or args. Keep an override on each command so the simple path stays simple.

Run-now vs. record

If populating launches immediately, what happens when you re-run it on a desktop that's already populated — top up, skip what's open, or start clean? (The apply flow already has to answer this.)
